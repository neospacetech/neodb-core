# Releasing NeoDB Core

Releases use GitHub Actions and PyPI Trusted Publishing. No PyPI API token is
stored in GitHub. The `release.yml` workflow exchanges GitHub's short-lived OIDC
identity for a project-scoped publishing token.

## One-time registry setup

The repository environments are named `pypi` and `testpypi`. Keep required
manual approval enabled for `pypi`.

Create pending trusted publishers in both registry accounts with these exact
claims:

| Setting | PyPI | TestPyPI |
| --- | --- | --- |
| Project | `neodb-core` | `neodb-core` |
| Owner | `neospacetech` | `neospacetech` |
| Repository | `neodb-core` | `neodb-core` |
| Workflow | `release.yml` | `release.yml` |
| Environment | `pypi` | `testpypi` |

Configure PyPI at <https://pypi.org/manage/account/publishing/> and TestPyPI at
<https://test.pypi.org/manage/account/publishing/>. The accounts are separate.
A pending publisher reserves the project through its first trusted
publication; do not create a long-lived `PYPI_API_TOKEN`.

## TestPyPI dry run

1. Set a unique development version in `pyproject.toml`, because registry
   versions cannot be overwritten.
2. Run the **Release** workflow manually from the Actions page.
3. Approve the `testpypi` deployment if that environment is protected.
4. Inspect the TestPyPI project and install from both TestPyPI and PyPI:

   ```bash
   python -m pip install \
     --index-url https://test.pypi.org/simple/ \
     --extra-index-url https://pypi.org/simple/ \
     neodb-core==<version>
   ```

Manual dispatch builds and verifies the wheel and source distribution, then
publishes only to TestPyPI. It never creates a GitHub release or publishes to
PyPI.

## Production release

1. Update `project.version` in `pyproject.toml` and merge it to `main`.
2. Wait for the main-branch CI run to pass.
3. Create and push the exact version tag:

   ```bash
   git tag -s v<version> -m "NeoDB Core v<version>"
   git push origin v<version>
   ```

The workflow rejects a tag that is not exactly `v` plus `project.version`. It
runs all quality gates and tests, builds and checks both distributions,
generates GitHub release notes, attaches the wheel and source archive, and then
waits for approval on the protected `pypi` environment. Approval publishes
through OIDC and includes the attestations generated by the PyPA publishing
action.

## Failed release recovery

- Before PyPI publication, fix the cause, delete the failed Git tag and GitHub
  release if one was created, then create the corrected tag.
- After any file reaches PyPI, never reuse or overwrite that version. Yank an
  unusable release if appropriate, increment `project.version`, and publish a
  new tag.
- If GitHub release asset upload alone fails, rerun the failed workflow jobs.
  The asset step replaces files on that same GitHub release; it does not bypass
  the PyPI environment approval.
- For an OIDC `invalid-publisher` failure, compare owner, repository, workflow
  filename, and environment against the table above. These claims must match
  exactly on the registry.
